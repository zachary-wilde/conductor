# On-device remote-access verification runbook

Turnkey procedure for verifying the Conductor Android app against a real PC Core
over the LAN. Assumes a competent operator with **zero project context**. The
phone is the client; the PC is the Core (the operations web server). Non-loopback
binds use HTTPS by default and include the certificate fingerprint in the pairing
code; loopback remains plaintext.

> **Mental model.** The PC runs a small HTTP+SSE server (the *Core*). The phone
> app is a thin web client that points at one Core URL + token. Pairing is just
> "tell the phone the Core's LAN URL and its access token" — either by scanning
> a QR, pasting a `C1:` code, or typing the two values. Once paired, the phone
> remembers them across relaunches.

---

## 1. Prerequisites

1. **Same network.** The phone and the PC must reach each other over IP — same
   Wi-Fi LAN, or a VPN that gives the PC an address the phone can route to.
   - Hotel/cafe/enterprise "client isolation" Wi-Fi and most guest networks
     **block phone↔PC traffic** even on the same SSID. If pairing fails and you
     are on guest Wi-Fi, switch to a phone hotspot or a home/office LAN.
2. **The PC's LAN IP.** Find it now: `ipconfig` → look for the IPv4 on the
   adapter the phone shares (e.g. `192.168.1.50`). You'll need this for manual
   entry and to sanity-check the pairing URL.
3. **Windows Firewall — allow inbound on the Core's web port.**
   **This is the #1 reason "it won't connect."** By default Windows blocks
   inbound TCP to a new server.
   - The headless helper listens on **`8787`** by default (override with
     `--port`). If you start the desktop app yourself, the port is whatever
     `CONDUCTOR_WEB_PORT` is set to (ephemeral if unset — read it from the
     printed URL).
   - Easiest one-time allow (run **as Administrator** in PowerShell); replace
     `8787` with your port:
     ```powershell
     New-NetFirewallRule -DisplayName "Conductor Core (LAN)" -Direction Inbound `
       -Protocol TCP -LocalPort 8787 -Action Allow -Profile Private
     ```
   - Or use **Windows Defender Firewall → Advanced Settings → Inbound Rules →
     New Rule… → Port → TCP → 8787 → Allow**, scoped to **Private** (not Public).
4. **The signed APK** on the phone's storage or downloadable: `conductor-release.apk`
   (repo root after a release build). The debug build (`conductor-debug.apk`)
   also works for verification.
5. **The PC Core built.** For the headless path you need one prior
   `npm run build` (it consumes `out/main/core.js` + `out/web`). The desktop-app
   path needs the installed/running app.

---

## 2. Enable remote access on the PC (pick one)

You only need **one** of these. Both expose the same Core; both print a QR and a
`C1:` pairing code. Either way, **the Core binds to `0.0.0.0`** (all interfaces)
so the phone can reach it, and **a token is auto-generated** because the server
is no longer loopback-only — it is **never blank on the LAN**.

### (a) Desktop app — Settings → Remote access

1. Launch Conductor on the PC with the Core bound to the LAN. From a terminal:
   ```powershell
   $env:CONDUCTOR_WEB_HOST = "0.0.0.0"
   $env:CONDUCTOR_WEB_PORT = "8787"   # optional; pins the port
   npm start
   ```
   Wait for the console line
   `[operations] web server listening on https://<this-machine-LAN-IP>:8787`
   The access token and pairing code are shown in **Settings → Remote access**.
2. In the app open **Settings → Remote access**. You'll see:
   - A **QR code** (scan from the phone), and three copyable rows:
     - **Core URL** — e.g. `https://192.168.1.50:8787`
     - **Access token** — the auto-generated bearer token
     - **Pairing code** — the `C1:…` string
   - If it reads *"Bound to loopback…"*, the Core did not bind to the LAN:
     restart with `CONDUCTOR_WEB_HOST=0.0.0.0`, then click **Refresh**.
3. Use **Refresh** after any restart to repopulate the QR/code (the token is
   stable for the life of the data dir unless you clear it).

### (b) Headless — `npm run remote-access`

Boots **only the Core** (no desktop window) bound to `0.0.0.0`, auto-generates a
token, and prints the URL + token + `C1:` code **and a terminal QR**. Use this
when you don't want the full desktop UI, or on a headless/CI machine.

```powershell
npm run build          # once — the helper needs out/main/core.js + out/web
npm run remote-access  # = node scripts/remote-access.mjs
```

Optional flags:

| Flag | Default | Notes |
| --- | --- | --- |
| `--port` | `8787` | The Core's web port. |
| `--base` | `%APPDATA%\conductor` | The Core's user-data dir. Use a different one to run beside the desktop app (the Core holds a single-instance lock per data dir). |

It prints:

```
URL:   https://192.168.1.50:8787
Token: <auto-generated>
Code:  C1:eyJ1Ijo...

Scan this in the Conductor app (or paste the code above):
<terminal QR>

Core is running. Press Ctrl+C to stop.
```

- **Leave this terminal open** — closing it stops the Core.
- If it exits immediately with *“lock held? try --base or close the desktop
  app”*, the desktop app (or a prior run) owns that data dir: close it, or pass
  `--base <some-other-dir>`.
- The same URL/token/code are also written to
  `<base>\conductor-data\web-endpoint.json` for scripting.

> **Note on the token.** Whenever the Core binds beyond loopback it mints a
> bearer token (set `CONDUCTOR_WEB_TOKEN` to pin your own). It is sent as
> `Authorization: Bearer <token>` on every API call. It is **never** blank on
> the LAN.

## 3. Pair the phone

1. **Sideload the APK.** Copy `conductor-release.apk` to the phone and open it.
   - Android will warn about "install unknown apps" — allow installs from your
     file browser for this one install, then proceed.
   - The release APK is signed (`CN=Conductor, OU=Dev, O=Conductor, C=CA`); you
     can verify with `apksigner verify --print-certs conductor-release.apk`.
2. **Open Conductor.** If no Core is paired yet, the **Connect** screen opens
   automatically (it also re-opens any time the opening handshake fails).
3. **Pair — any one of:**
   - **Scan QR** (if the device has a camera + `BarcodeDetector`): tap
     *Scan QR* and point it at the desktop panel's QR (or the terminal QR).
   - **Paste the `C1:` code** into the *Or pair with a code* box → **Use code**.
     Surrounding whitespace/newlines are trimmed, and **the `C1:` prefix is
     optional** — pasting just the payload works too.
   - **Type it manually**: enter **Core URL** (`https://<PC-LAN-IP>:8787`) and
     **Access token** into the top fields → **Connect**.
4. The app **persists the base URL + token** to local storage and reloads, so
   the pairing survives app relaunches and phone reboots. To un-pair later, open
   Connect (tap the host chip in the top bar) → **Forget**.

The handshake runs immediately. On success you land on the **live timeline**.

## 4. Verification checklist

Walk these on the phone. Each item is something to **click and a result to
expect**. A working Core + a repo with at least one worker and one open review
branch gives you the full path.

- [ ] **Timeline streams live.** New operator events (worker status changes,
  file activity, ravel/roundtable turns) appear without a manual refresh. The
  connection chip in the top bar reads **connected** (lock icon when a token is
  set).
  - *Behind the scenes:* the live tail is an SSE stream. The app authorizes it
    with a **short-lived, single-use ticket** — it POSTs the bearer token to
    `/api/sse-ticket` and opens the stream with that ticket, so **the token is
    never in a URL or a log**. Nothing for you to do; just know the bearer never
    appears on the wire as a query string.
- [ ] **Workers → controls.** Open a worker. Exercise each control and confirm
  the Core acknowledges it:
  - **Message** — type and send; the message is delivered.
  - **Pause / Resume** — state toggles and is reflected in the worker detail.
  - **Stop** — requires a two-step confirm; on confirm the worker stops.
  - **Retry** — re-queues the worker.
  - **Archive** — removes the worker from the active roster.
  - **Detach** — opens a **dedicated confirm panel that NAMES the dependent
    brief(s)** blocking this worker (e.g. *"Detaching this worker blocks N
    dependent brief(s): …"*). Only **Confirm detach** actually detaches
    (`worker.control {action:'detach', confirmed:true}`). If there are no
    dependents the panel says so. **Confirm the dependent names are correct
    before detaching.**
- [ ] **Automations.** Open **Automations**: the list of definitions loads, each
  with its schedule/cadence and recent **occurrences**. Toggle **enabled**, and
  if an occurrence needs approval, **Approve** it and confirm the Core records
  the occurrence.
- [ ] **Review a branch → diff viewer.** Open **Review**. For a branch card:
  - Tap **View diff**. The per-file view loads: each file shows a header (path,
    status badge — added/deleted/modified/renamed, and `+add/-del` counts) and
    **colored unified-diff hunks** (additions green, deletions red, context
    muted).
  - Confirm the **binary / oversized / truncated** states render as an amber
    *"not shown"* note instead of empty/garbled text (e.g. point a branch at a
    repo with an image or a very large file).
  - If the branch advanced on the PC since you loaded the diff, the viewer flags
    it (re-open to refresh).
- [ ] **Review decisions.** On a review card:
  - **Land** — on a verified branch this is one click; on an unverified/failed
    branch it gates behind an explicit confirm bar. Confirm the land reaches the
    Core and the card drops when the branch is removed.
  - **Request changes** — requires a non-empty note; confirm it is sent.
  - **Reject** — requires a non-empty note; confirm the card is disposed.
- [ ] **Reconnect resilience (optional but recommended).** With the app open and
  streaming, stop the PC Core (Ctrl+C the helper, or quit the desktop app). The
  chip flips to **reconnecting/offline** with backoff; it does **not** crash.
  Restart the Core — the timeline reconnects and resumes on its own. Trigger a
  burst of >300 API calls in 60s from one IP to confirm the **429 rate-limit
  banner** appears with a live countdown and the app recovers when the window
  resets.

## 5. Troubleshooting

| Symptom (what you see) | Likely cause | Fix |
| --- | --- | --- |
| **Handshake fails / 401 Unauthorized** on Connect | Wrong or expired token; or a stale ticket for the SSE stream. | Re-copy the **Access token** from the desktop Remote-access panel (or the helper's `Token:` line) and re-paste. Re-pair via the `C1:` code to set both URL + token at once. A 401 specifically means the URL was reached but the bearer was wrong/missing. |
| **Connection refused / ERR_CONNECTION_REFUSED** | Core not reachable: Windows Firewall blocking the port, wrong IP, or the Core bound to loopback only. | (1) Confirm the Core is running and bound to `0.0.0.0` (`CONDUCTOR_WEB_HOST=0.0.0.0`); the desktop panel must **not** say "Bound to loopback". (2) Add the inbound firewall rule (§1.3). (3) Re-check the IP — use the PC's LAN IPv4, not `127.0.0.1` or `localhost`. (4) On guest/isolation Wi-Fi, switch networks. |
| **TLS/certificate warning or handshake failure** | The LAN Core uses its persisted self-signed certificate, which the Android WebView will not trust. | Pair with the current `C1:` code so the URL and fingerprint are current. If the phone still cannot connect, run the Core with `CONDUCTOR_WEB_TLS=0` (cleartext over your trusted LAN — the token still applies) and pair again over `http://`. |
| **Pairing code rejected** ("not a valid pairing code") | Code is truncated, copy-pasted with missing characters, or from a Core that has since restarted with a new token. | Re-copy the **full** `C1:…` string (the `C1:` prefix is optional, but the payload must be complete). If the Core was restarted and auto-generated a new token, re-pair with the fresh code. The token in an old code is stale. |
| **403 Forbidden on `/api`** | DNS-rebinding guard rejected the request because you reached the Core via a **DNS hostname** instead of an IP. | Use the **LAN IP** (`https://192.168.1.50:8787`), not a machine name or mDNS name. The pairing URL already uses the IP, so this only bites if you typed a hostname manually. |
| **Timeline stalls / no live updates, but Connect succeeds** | SSE ticket expired or the stream dropped and is mid-backoff. | Usually self-heals (the chip shows `reconnecting`). If stuck, tap the host chip → **Forget**, then re-pair to force a clean handshake + fresh ticket. |
| **429 Too Many Requests / rate-limited banner** | >300 API requests from the phone's IP in 60s (the fixed-window limit). | Wait for the banner countdown to elapse; the app auto-resumes. Normal interactive use never hits this. |

## 6. What this does NOT cover yet

This runbook verifies the **current** remote-access transport, which is:

- **HTTPS by default** for non-loopback binds. The Core persists a self-signed
  certificate and includes its SHA-256 fingerprint in the `C1:` pairing code.
  Loopback binds remain plaintext by default.
- Protected by: the **bearer access token** (auto-generated on LAN bind),
  **permissive CORS** for the web client, a **fixed-window rate limit**
  (300 req/60 s per IP), and a **DNS-rebinding Host guard** (IP/localhost only).
- The SSE live stream is further protected by **short-lived, single-use tickets**
  so the bearer never appears in a URL.

**Native certificate pinning is not built.** A WebView client cannot meaningfully
pin a certificate without a native pinning layer, so verify the fingerprint in the
pairing code and run the Core on a trusted network. For the Android client, which cannot
trust a self-signed certificate, run the Core with `CONDUCTOR_WEB_TLS=0` to serve cleartext
over a trusted LAN (the access token still gates every request).
